## Getting Started

First, we need to install the k6 for load testing.
```bash
curl -sLS https://get.arkade.dev | sudo sh
arkade get k6
echo 'export PATH=$PATH:$HOME/.arkade/bin' >> ~/.bashrc && source ~/.bashrc
k6 version
```
Once k6 has successfully installed, we cna proceed with the stress testing process.

## Testing process

We modify the `.env` file to change to our own topic, group ID, and notification URL for testing. Further on, we start the local notifications-service using the scripts in the `producer/` directory and it should print that the service has opened. In this directory, we also have the `producer.env` file which holds the brokers, topic and secret key for initiating the experiment-producer and notifications-service. 
```bash
cd cec-project
chmod +x producer/notifications.sh
./producer/notifications.sh
```

After the notifications-service has started, we can also verify the success of the container by running the following command:
```bash
curl -i -X POST http://localhost:3000/api/notify \
    -H 'Content-Type: application/json' \
    -d '{"notification_type":"OutOfRange","researcher":"x","measurement_id":"1","cipher_data":"x"}'
```
This should get an HTTP response that complaines about the fake `cipher_data`, suggesting that the service runs. 

Follwing the confirmation that the notifications-service is up and running, we can start our own system to analyse:
```bash
docker compose up -d --build
# and also check the logs for the consumer
docker compose logs -f consumer
```

There are three main types of tests that we perform, the first one is to verifying whether everything in the system works as intended, and then the second and third testing are designed to stress-examine the different parts of the system and at the same time. To run the first check:
```bash
chmod +x producer/experiment.sh
cd producer
python3 config_generator.py 5
./experiment.sh
# to check whether the events are produced
docker logs -f experiment-producer
```
These commands initiate the experiment-producer, then runs the script for generating 5 experiments and finally, starts the producer. After some time, the consumer can be checked to observe lags and whether experiments are being written to the database:
```bash
docker compose logs --tail=30 consumer
docker compose exec db sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "SELECT count(*) FROM temperatures;"'
```

To finally check with k6, we use the next command:
```bash
cd cec-project
k6 run -r BASE_URL=http://localhost:3003 -e VERIFY=1 stress-test/api_load.js
```

To stress-test the consumer, we create about 100 experiments and observe whether the consumer can maintain a higher load of experiments.
```bash
cd ~/cec-project/producer
python3 config_generator.py 100
./experiment.sh
# watch the logs in different terminals
docker compose logs -f consumer | grep -E "lag|notif"
docker stats
```
One new experiment starts every 2 seconds, so after about 3.5 minutes all 100 of them are running, which is around 350 events per second. 

To stress-test the API, we execute the script `stress-test/api_load.js`. For this, the producer can be stopped.
```bash
k6 run -e BASE_URL=http://localhost:3003 --summary-export=summary-api.json stress-test/api_load.js
```
This takes about 8 minutes to run, we use `docker stats` alongside to observe the CPU usage. 

To stress-test the system on both the consumer and API, we use the respective commands accordingly:
```bash
python3 producer/config_generator.py 100 && ./producer/experiment.sh
# wait for a few minutes to consume some experiments and then test the API
k6 run -e BASE_URL=http://localhost:3003 --summary-export=summary-combined.json stress-test/api_load.js
```

In all the cases above, the logs offer the information needed to determine whether the service passes the tests. However, to analyse the important aspects, we created a monitoring script for the logs and a respective Python file that analyses the generated monitoring files. Before running any testing, run the `monitor.sh`:
```bash
chmod +x stress-test/monitor.sh
./stress-test/monitor.sh <run-name>
```
This creates a dedicated folder of results within the stress-test directory to store the log files of the system while running the tests. After the finalisation of a test, the CSV file generated by the monitoring technique can be analysed using:
```bash
python3 stress-test/analyse.py stress-test/results/<run-name>
```
